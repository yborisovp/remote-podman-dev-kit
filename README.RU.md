# Remote Podman Dev Kit

Запускайте сервисы **своего Compose-проекта** на Linux с rootless Podman, управляя ими из macOS или Windows RDP / Git Bash. Исходники и команды идут по SSH; порты доступны на localhost рабочей машины.

[English](README.md)

```bash
./dev.sh
```

В меню выберите **Server setup → Full installation**, затем **Check connection** и **Start services + tunnels**. Стрелки или j/k перемещают выделение, номер выбирает пункт, Enter подтверждает, q возвращает назад. В списке сервисов номер переключает отметку, a выбирает все, n снимает отметки. После действия Enter возвращает в меню. `NO_COLOR=1 ./dev.sh` отключает цвета.

## Размещение в вашем проекте

Скачайте `remote-dev.tar.gz` из [последнего стабильного GitHub Release](https://github.com/yborisovp/remote-podman-dev-kit/releases/latest) (или из артефактов задания **package** в GitLab CI) и распакуйте в нужный репозиторий. Архив содержит одну папку `remote-dev/`; её можно переименовать или переместить. Скрипты и конфигурация остаются внутри неё.

```bash
tar -xzf remote-dev.tar.gz -C /path/to/project
cd /path/to/project
./remote-dev/dev.sh
```

Compose сначала ищется рядом с `dev.sh` (предпочтительный вариант), затем на один уровень выше. Если рядом есть несколько основных Compose-файлов, укажите `COMPOSE_FILE`; перехода к родительской папке в этом случае нет. Для другого расположения задайте `PROJECT_DIR` в `config/dev.env`: абсолютный путь или путь относительно папки комплекта. `COMPOSE_FILE` и `COMPOSE_OVERRIDE` задаются относительно корня проекта; именно этот корень передаётся на сервер. Конфиг, список обязательных адресов и `.runtime` остаются в папке комплекта. Не перемещайте комплект при работающем туннеле: сначала закройте его.

Для самостоятельной сборки архива: `bash scripts/package.sh`. GitLab CI запускает проверки и создаёт `dist/remote-dev.tar.gz`. В архив по явному списку включаются только рабочие файлы и инструкции, без локального конфига, ключей и временных данных. CI этого комплекта не требуется добавлять в целевой проект.

Автоматически ищутся `compose.yaml`, `compose.yml`, `docker-compose.yaml`, `docker-compose.yml`. При отсутствии файла или наличии нескольких кандидатов запуск останавливается с пояснением. Можно явно задать относительный путь через `COMPOSE_FILE`. При автоматическом поиске подхватывается единственный `compose.override.yaml/yml` или `docker-compose.override.yaml/yml`; для явного основного файла задавайте override через `COMPOSE_OVERRIDE`.

**Список сервисов берётся только из Compose.** Старый `examples/services.conf` удалён; переключения на демонстрационные сервисы нет. Примеры и тесты не нужно копировать в ваш репозиторий. При переносе добавьте правила из `.gitignore` в существующий `.gitignore`, не заменяя его.

Для демонстрации скопируйте `examples/compose.yaml` в корень этого набора как `compose.yaml`, создайте `.env` с `POSTGRES_PASSWORD=<ваш-пароль>` и запустите меню. Не копируйте демонстрационный Compose поверх собственного файла.

## Автоматические сборки и релизы на GitHub

GitHub Actions выполняет проверки на Ubuntu и macOS после push в `main` и для каждого PR в `main`. Проверяются сценарии SSH/Compose с имитацией сервера, терминальное меню, модульные тесты и распакованный архив. Реальная установка Debian в CI не выполняется.

После успешной проверки всех платформ автоматически публикуются:

- **main:** стабильный релиз с тегом `vX.Y.Z`, архивом и SHA-256. Учитываются сообщения всех коммитов после предыдущего стабильного тега: отдельное слово `major` повышает X, `minor` — Y, `patch` — Z. Регистр не важен; приоритет `major > minor > patch`. Без метки повышается patch. Примеры: `[minor] Add feature`, `[patch] Fix login`, `[major] Change configuration`. При повышении major/minor младшие части сбрасываются. Тексты PR учитываются только если попали в сообщение коммита при слиянии.
- **PR:** prerelease с тегом `pr-<номер>-build-<run_id>-<попытка>`. Каждая успешная попытка получает отдельный тег; такие сборки не меняют `Latest` и не влияют на стабильную нумерацию. Это архив конкретного head-коммита PR, включая PR из форков. Устанавливайте сборки только от авторов, которым доверяете.

Вкладка **Actions → Verify and package → Run workflow** на `main` позволяет повторить проверки и восстановить незавершённую публикацию. Уже опубликованный релиз того же коммита остаётся неизменным. Если во время проверки `main` обновился, устаревшая сборка не публикуется: следующий успешный актуальный запуск выпустит все накопленные изменения. Стабильные публикации выполняются последовательно; файлы загружаются до открытия релиза. Артефакты CI хранятся 14 дней, файлы опубликованных релизов остаются доступными.

Публикация запускается отдельным `workflow_run` из доверенной ветки `main`. Сборки PR имеют только права чтения; workflow публикации не распаковывает и не исполняет их архивы. Используется встроенный `GITHUB_TOKEN`: право `contents: write` есть только у задания публикации. Секрет PAT не нужен. Правила организации/репозитория должны разрешать GitHub Actions и создание тегов `v*` / `pr-*-build-*` этим токеном. Создание тега и релиза происходит в одном workflow, поэтому не зависит от повторного запуска Actions событиями этого токена.

Локальная полная проверка: `bash scripts/verify.sh` (нужны Python 3 и PyYAML). GitLab CI использует ту же команду и продолжает выпускать архив как артефакт без публикации релиза.

## Требования и первая настройка

На рабочей машине нужны Bash 3.2+, OpenSSH и tar: macOS Terminal или Git Bash. Локальный Docker Engine, Podman, Compose, Python, WSL и виртуальная машина для запуска набора не требуются. `nc` необязателен для предварительной проверки локальных портов; окончательную проверку выполняет SSH.

На Linux нужны rootless Podman, пользовательский Podman socket, Compose-провайдер (`docker-compose` либо `docker compose`), Python 3 и `python3-yaml` для Compose v1. Провайдер подключается к Unix-сокету Podman проектного пользователя; Docker Engine для запуска сервисов не используется. Совместимость конкретных Compose-возможностей зависит от провайдера и Podman.

При выборе настройки конфиг создаётся автоматически. `PROJECT_NAME` выводится из имени папки; проверьте, что он уникален среди проектов одной Linux-учётной записи. Для изоляции разных разработчиков и границ доверия используйте отдельные Unix-учётные записи.

**Полная установка:** в меню **Server setup → Full installation** укажите SSH-алиас или адрес обычного пользователя с sudo (либо root) и имя будущего Linux-пользователя. Предлагается имя рабочего пользователя; в Git Bash дополнительно показываются профили `/c/Users`. Скрипт показывает план и просит подтвердить изменения сервера.

На Debian/Ubuntu с systemd полная установка:

1. Подключается по SSH с вашими настройками `~/.ssh/config` и при необходимости вызывает `sudo` с запросом пароля в терминале и проверяет TCP-доступность обязательных адресов из `config/required-endpoints.conf` через `nc` либо `/dev/tcp` с тайм-аутом. Неудача останавливает установку до изменения пакетов.
2. Устанавливает отсутствующие Podman, rootless-зависимости, Python 3/PyYAML, `docker.io` и Compose через apt. Включает Docker service согласно сценарию полной установки; Docker работает с root-привилегиями, пользователь проекта в группу docker не добавляется.
3. Создаёт пользователя и домашнюю папку или использует указанного существующего пользователя, назначает Bash. При необходимости добавляет свободные диапазоны subordinate UID/GID минимум по 65 536 ID.
4. Добавляет открытый Ed25519-ключ, выставляет права `.ssh`/`authorized_keys`, включает linger и пользовательский Podman socket. Пароль Linux-пользователя не задаётся и не изменяется.
5. Записывает пользовательский SSH-адрес в `PODMAN_HOST` и проверяет rootless-режим.

Root SSH-политика не изменяется. При первом подключении проверьте fingerprint. Выберите парольную фразу ключа и загрузите ключ в `ssh-agent`; пароль и парольная фраза не сохраняются. Установка не атомарна: после ошибки проверьте сообщение и повторите её; выполненные шаги остаются.

**Нужен ли заранее SSH-ключ?** Должен работать обычный `ssh ваш-алиас`: по уже установленному ключу или паролю, если сервер разрешает парольный вход. При полной установке заранее добавлять новый проектный ключ не нужно: скрипт создаёт его локально и добавляет открытый ключ проектному пользователю через административный вход. Приватный ключ на сервер не передаётся. Если ключ защищён парольной фразой, загрузите его в `ssh-agent` перед `check` и запуском сервисов: `ssh-add /путь/из/SSH_KEY`. Эти команды работают без интерактивного запроса пароля.

Поле `SSH_PORT` оставьте пустым для порта из SSH-алиаса; явное значение переопределяет настройки SSH. Алиас сохраняется и при подключении новым пользователем: `project-user@ваш-алиас`. Настройки алиаса должны допускать смену пользователя, включая настройки ProxyJump/Match, если они используются.

**Готовая учётная запись:** выберите **Server setup → Connect existing user** и укажите `user@host` либо SSH-алиас. Предварительные зависимости должен подготовить администратор. Этот режим использует существующий SSH-доступ и не создаёт новый ключ. Пустой `SSH_KEY` сохраняет выбор ключа из SSH config/agent.

## Ручное выделение пользователя

Пример для администратора Debian/Ubuntu, если полный режим не используется:

```bash
sudo apt-get update
sudo apt-get install -y podman uidmap slirp4netns fuse-overlayfs dbus-user-session openssh-server python3 python3-yaml docker-compose
sudo useradd --create-home --shell /bin/bash myapp-dev
```

Проверьте диапазоны в `/etc/subuid` и `/etc/subgid`. Если диапазона минимум из 65 536 ID нет, назначьте свободный. Пример ниже допустим **только после проверки отсутствия пересечений с другими пользователями**:

```bash
grep '^myapp-dev:' /etc/subuid /etc/subgid
sudo usermod --add-subuids 200000-265535 --add-subgids 200000-265535 myapp-dev
sudo loginctl enable-linger myapp-dev
```

Установите открытый SSH-ключ рабочей машины: создайте `/home/myapp-dev/.ssh` с владельцем `myapp-dev` и правами 700, поместите содержимое публичного `.pub` в `authorized_keys` с тем же владельцем и правами 600. Приватный ключ остаётся на рабочей машине. Это обеспечивает первоначальный вход без назначения пароля новому пользователю. Затем выберите **Connect existing user**. При этом входе скрипт включит пользовательский socket и проверит `podman info --format '{{.Host.Security.Rootless}}'`, ожидая `true`.

## Что происходит при запуске

1. Скрипт находит Compose и создаёт защищённый снимок исходников на Linux по SSH.
2. Серверный Compose выполняет `config`: разрешает `.env`/`env_file`, объединяет основной файл с override, нормализует сервисы, сети, тома, сборки и порты.
3. Меню показывает фактические сервисы. Для выбранных сервисов учитываются зависимости; поддерживаются несколько TCP-портов и сервисы без опубликованных портов.
4. Адаптер записывает отдельный нормализованный Compose, привязывая все опубликованные порты к `127.0.0.1` Linux. Исходный Compose-файл не меняется. Явный `container_name` убирается, чтобы Compose создавал имена в пространстве `PROJECT_NAME`.
5. Compose запускает выбранные сервисы и зависимости с удалённой сборкой. Для их опубликованных TCP-портов открываются SSH local forwards.

Например, `8080:80` становится `127.0.0.1:18080:80` на сервере при `REMOTE_PORT_OFFSET=10000`. На рабочей машине сервис доступен на `127.0.0.1:8080`. `expose` не создаёт туннель. Одинаковые опубликованные порты отклоняются; занятые порты проверяются при запуске и привязке SSH.

Перед новой выборкой сервисов остановите текущий проект через **Stop all services (keep volumes)**. Это выполняет Compose `down` без удаления именованных томов. Остановка выбранных сервисов выполняет `stop`; общий туннель закрывается. **Close tunnel only** оставляет контейнеры запущенными. Status и Stop используют сохранённую удалённую конфигурацию, даже если локальный Compose уже изменён.

## Конфигурация

`config/dev.env` — простые строки `KEY=value`, которые не исполняются как shell-код. Не заключайте значения в кавычки.

| Параметр | Назначение |
|---|---|
| `PODMAN_HOST` | Первая настройка: пользовательский SSH-адрес или алиас. |
| `ROOT_HOST` | Административный SSH-адрес или алиас полной установки (sudo либо root). |
| `SSH_PORT` | Пусто — настройки OpenSSH; значение переопределяет порт алиаса. |
| `SSH_KEY` | Путь к локальному приватному ключу, записывается настройкой. |
| `PROJECT_NAME` | Уникальное имя Compose-проекта: строчные латинские буквы, цифры, `_`, `-`. |
| `REMOTE_BASE` | Относительный каталог в домашней папке Linux; по умолчанию `.cache/remote-podman-dev`. |
| `PROJECT_DIR` | Пусто — каталог комплекта, затем родитель; иначе абсолютный путь или путь относительно комплекта. |
| `COMPOSE_FILE` | Пусто — автоматический поиск в выбранном корне проекта; иначе относительный путь. |
| `COMPOSE_OVERRIDE` | Дополнительный Compose-файл. |
| `REMOTE_PORT_OFFSET` | Прибавка к опубликованному порту для серверного порта; по умолчанию 10000. Серверный порт должен быть в 1024–65535. |
| `REQUIRED_ENDPOINTS_FILE` | `host\|port\|description` для полной установки; по умолчанию `config/required-endpoints.conf`. |

Перед запуском проверяется TCP-доступ к реестрам готовых образов выбранных сервисов. Хосты базовых образов Dockerfile и package feeds добавляйте в обязательные адреса вручную. TCP-проверка не проверяет TLS, авторизацию и HTTP; ошибка pull/build выводится отдельно. Локальные переменные оболочки на сервер автоматически не передаются: используйте `.env` проекта или `env_file`.

## Передаваемые файлы и ограничения

**`.env`, `env_file` и файловые secrets передаются по SSH в домашний каталог проектного пользователя.** Нормализованный Compose может содержать секреты; сохраняется с правами 600. Снимки создаются под `umask 077`. Не передавайте проект учётной записи, которой не доверяете эти данные.

При расположении комплекта в подпапке его `config/dev.env` и `.runtime` также исключаются. Из передачи исключены `.git`, `.runtime`, `config/dev.env`, `node_modules`, `bin`, `obj`, `__pycache__`. Дополнительные tar-паттерны исключений можно указать в `.devkitignore`. Не исключайте файлы, необходимые Compose или сборке. Учитывайте `.dockerignore` внутри контекстов сборки.

Контексты сборки, файловые secrets/configs и bind mounts должны находиться внутри передаваемого проекта. Абсолютные пути рабочей машины, внешние каталоги, remote build contexts и дополнительные build contexts не поддерживаются. SSH build forwarding также не поддерживается. Снимки сохраняются на сервере для диагностики; автоматического удаления нет. Bind mounts указывают на снимок, изменения в нём не возвращаются на рабочую машину. Для постоянных данных используйте именованные volumes. Для live reload потребуется отдельная синхронизация.

Отклоняются host/container networking, опубликованные UDP-порты, диапазоны и случайные порты. Профили включены для перечисления всех сервисов; запускаются выбранные и их зависимости. Проект не предназначен для production-развёртывания. Частично завершившийся `up` не откатывается автоматически: используйте Status и Stop all. После аварийного завершения может потребоваться вручную удалить `.runtime/operation.lock`, предварительно убедившись, что операция больше не работает.

## Проверки

```bash
bash tests/smoke.sh
python3 tests/ui_smoke.py
python3 -m unittest discover -s tests -p 'test_*.py'
```

Python нужен для локальных тестов, но не для работы launcher. Smoke-тест запускает настоящий серверный адаптер в временной папке с имитацией SSH/Compose: проверяются обнаружение файла, зависимости, несколько портов, передача файлов, старт/стоп и туннель. UI проверяется в псевдотерминале macOS/Linux. Это не проверка реального Linux-сервера, Podman API или Windows RDP. ShellCheck можно запустить отдельно: `shellcheck dev.sh setup.sh lib/ui.sh tests/smoke.sh`.

Официальные источники: [Compose config](https://docs.docker.com/reference/cli/docker/compose/config/), [Compose-провайдеры Podman](https://docs.podman.io/en/latest/markdown/podman-compose.1.html), [rootless Podman](https://docs.podman.io/en/latest/markdown/podman.1.html#rootless-mode).
